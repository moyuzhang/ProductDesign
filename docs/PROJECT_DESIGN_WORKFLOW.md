# 项目设计推进协议

版本：1.1.0  
状态：强制执行  
主实体：画布交付节点（DiagramNode）

## 1. 目标

让人和 Agent 只凭项目 ID 就能确定：项目当前做到哪里、缺少什么、唯一下一步是什么，并保证 Web、API 和 MCP 不能跳过关键门禁。

## 2. 标准顺序

```text
了解项目
  → 项目简报
  → 系统主画布
  → 模块和功能节点
  → 节点定义与验收标准
  → 需求评审
  → 按需详细设计
  → 开发计划
  → 开发实施
  → 测试与证据
  → 验收关闭
```

项目简报只需要覆盖目标、用户、范围、非目标、现状、约束和成功标准。所有文档统一属于当前项目系统；节点、画布、计划、数据库模型和证据只引用文档版本，不拥有文档。

## 3. 接手项目的读取顺序

1. 调用 `get_project_workflow`。
2. 读取项目目标、范围、阶段、风险、阻塞和下一步。
3. 查看系统主画布和子画布，确认模块边界。
4. 查看交付节点的需求、设计、开发和验收状态。
5. 查看已批准文档和有效治理决策。
6. 查看开发计划、依赖、负责人和截止时间。
7. 查看数据库模型及节点表关联；旧项目先反向工程现有数据库。
8. 查看测试证据和审计记录。

`get_project_workflow` 返回的是项目关键路径，设计门禁与人工审批必须服从该动作。已由 Worker 池原子领取的并行施工任务以租约中的 `taskKey`、`taskRevision`、交付层和资源锁为准，不再要求与项目关键路径逐字相等。完成动作后重新读取工作流。

## 4. 交付节点

进入交付状态机的画布类型：系统主画布、功能架构图、部署架构图。

进入交付状态机的节点类型：模块、功能、需求、接口、数据。

流程图、用例图和自由画布只表达流程、参与者和辅助设计，不携带交付状态，也不能作为项目完成依据。

节点创建后应补充：

- 名称、所属画布和类型。
- 功能目标、职责边界和不负责的内容。
- 负责人。
- 输入、输出、依赖及异常情况。
- 可验证的验收标准。
- 是否需要数据库。

## 5. 文档与引用规则

| 时点 | 文档 | 引用对象 | 关系类型 |
|---|---|---|---|
| 了解项目 | 项目简报、现状说明 | 项目 | `defines` |
| 功能拆分后 | 需求文档、功能说明 | 画布、节点 | `defines` |
| 详细设计 | 接口、数据库、部署设计 | 节点、数据库模型 | `defines` |
| 开发实施 | 需求、接口和设计基线 | 计划 | `implements` |
| 关键选择发生时 | 相关设计说明 | 治理记录 | `references` |
| 测试后 | 测试报告、验收文档 | 证据 | `verifies` |

`DesignDocument` 是项目级文档唯一数据源，`DocumentRevision` 保存不可变版本，`DocumentReference` 保存业务对象到固定版本的多对多引用。删除节点、计划、画布、数据库模型或证据时只解除引用，不删除文档；删除文档时同时删除其版本和引用。

文档更新会产生新的 `DocumentRevision`，已有引用仍锁定旧版本并显示“版本已过期”。必须显式确认后才能把引用推进到当前版本，防止需求批准、施工和验收依据被静默替换。

节点开始开发前至少需要一份状态为“已批准”、且引用版本等于文档当前版本的文档。验收标准必须在开发前确定，测试报告和执行证据在验证后产生。

## 6. 数据库设计触发条件

功能需要持久化业务数据，或新增/修改表、字段、关系、索引、约束、迁移和审计时，节点必须标记“需要数据库”。

固定顺序：业务对象和生命周期 → 功能节点 → 数据职责 → 数据库模型 → 节点表关联 → 开发。

旧项目可在了解阶段先反向导入现有数据库，但导入结果是现状证据，不是目标设计。目标模型仍需由功能需求驱动。

## 7. 强制门禁

### 需求批准

- 功能说明完整。
- 已指定负责人。
- 验收标准可验证。

### 设计批准

- 需求已经批准。
- 至少一份节点当前引用的文档已经批准，且引用未过期。
- 需要数据库的节点已关联数据库表。

### 开始开发

- 项目摘要和已批准项目简报存在。
- 节点需求和设计已批准，或不涉及详细设计时明确标记设计不适用。
- 负责人、验收标准和已批准且未过期的节点文档引用存在。
- 至少一个绑定到该节点的开发计划存在。
- 需要数据库的节点已经完成表关联。

### 开发完成

- 全部节点开发计划已完成。
- 没有未解除阻塞。

### 验收通过

- 开发状态为已完成。
- 全部开发计划已完成。
- 验收标准存在。
- 至少一条可复核且通过的证据存在。
- `Evidence` 是验收证据的唯一持久化实体；节点通过 `nodeId` 关联证据，画布节点不再内嵌证据副本。
- 至少一份节点当前引用的文档已批准，且引用未过期。
- 需要数据库的节点已完成表关联。

## 8. Agent/MCP 约定

只读入口：

- `get_project_workflow`：完整阶段、节点门禁和下一步。
- `get_next_project_action`：唯一下一步动作。
- `validate_project_workflow`：完整缺失项检查。
- `list_document_references`：按项目、文档或目标对象读取引用。
- `create_document_reference`：创建锁定当前或指定文档版本的引用。
- `refresh_document_reference`：显式确认并推进到文档当前版本。

修改仍使用现有项目、画布、计划、文档、数据库和证据工具。所有画布交付状态变化必须经过统一后端门禁，MCP 不具备绕过权限。

### Worker 池、资源锁与任务租约

- 依赖任务的验收状态限制实现交付，不阻止下游节点定义、文档审批、设计提交、独立设计审计和设计计划批准。工作流、队列、领取和状态转换按实际动作一致判断；实现开工、实现审计通过及最终验收仍须满足上游依赖。真实循环或无效依赖仍阻止正向推进，设计可先行不豁免身份、文档、证据和资源锁门禁。

- 外部进程默认调用 `claim_next_agent_task`，由服务端按交付层、优先级、容量、阻塞状态和资源锁原子派发；`get_agent_task_package(taskId)` 仅保留给人工诊断和兼容客户端。
- 每个 Designer、Builder 和 Auditor 都必须提交与本人任务绑定的工单，至少写明 `taskKey`、`taskRevision`、实际产出或证据；未提交工单不得交接或宣告完成。
- `agentId` 表示计划角色身份，`poolId` 表示可承接该角色的 Worker 池，`workerId` 表示一个外部进程且必须唯一、稳定；同一 Worker 或会话一次只能持有一个有效任务。
- 同一项目、队列、任务和任务修订在任一时刻只能存在一个有效租约；已占用任务不会再次分配，编排器应领取当前层下一项可用任务。
- 领取时同时锁定任务的 `workScopes` 并预留独立工作区。范围重叠的任务不得并发；租约失效后资源锁按到期时间立即失效并由清理器回收。
- Agent 修改目标项目之前必须调用 `start_agent_task`，并发 Builder 必须提交独立 `workspacePath`、分支和基线修订；ProductDesign 只分配和校验，不创建 worktree、不启动外部进程。执行期间按任务包给出的间隔调用 `heartbeat_agent_task`。
- 受控计划的 Agent 流转必须同时提供 `leaseToken`、`agentId` 和 `idempotencyKey`；身份、任务、角色或租约任一不匹配时拒绝写入。
- `transition_plan_delivery` 成功后自动推进或关闭对应租约。失败或主动停止时使用 `fail_agent_task` 或 `release_agent_task`，使任务可重新领取。
- 租约过期后允许新执行者接管；旧执行者收到 `LEASE_LOST` 后必须立即停止，不能继续写入或提交状态。
- 施工计划批准和最终验收进入独立的 Main Agent `approval` 租约队列；必须在独立审计通过且证据完整后执行，拒绝时生成可追溯返工。只有 human-only 高风险执行授权保留在 `managerApproval` 人工门禁。

旧版 `list_work_nodes`、`update_work_node` 只用于兼容历史数据，不参与项目阶段和下一步计算。

## 9. 完成定义

一个节点只有在开发完成、计划全部完成、证据完整、文档已批准并验收通过后才算关闭。一个项目只有在全部交付节点关闭后才进入“已完成”。

协议的机器可读来源是 `src/shared/workflowPolicy.ts`；服务计算逻辑是 `src/server/workflow.ts`。若文档和门禁不一致，以后端门禁为准并立即修正文档。
